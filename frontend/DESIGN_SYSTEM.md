# Frontend design system

The initial application screen follows the `data-terminal` direction generated by the repository's `design-taste-frontend` skill with seed `20261101`.

## Product question

Can a researcher verify that true CHIRPS acquisitions for Beed travelled through Earth Engine, district-polygon aggregation, PostgreSQL and FastAPI without being presented as current or farm-level data?

## Visual direction

- Dense research-monitoring layout for long sessions.
- Public Sans for interface text; JetBrains Mono for every changing figure because dates, coverage and measurements must stack cleanly.
- Neutral dark ground (`#171719`) and surface (`#131217`), avoiding navy/slate tint.
- Rainfall blue (`#4a8ad6`) is restricted to the data line and 1px selection marks.
- Cards use one 6px radius and the style's low shadow; controls and statuses use pills only where they encode state.
- The product signature is the district acquisition timeline paired with source provenance and a row-level quality table.

## Responsive behavior

- Desktop uses a 54px icon rail and a chart/provenance split.
- Tablet folds the split into one column and the KPI strip into two columns.
- Phone converts the rail to a bottom bar, limits the chart to 200px, and converts the observation table to data-preserving two-line rows.

## Honesty rules

- No hardcoded fallback observation series.
- A failed API call shows an inline error and explicitly states that demo data was not substituted.
- The date window is labelled historical.
- District aggregation is labelled as not farm-level.
